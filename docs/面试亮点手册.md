## 亮点一：多级调度（配额感知 + 历史成功率加权）

### 一句话
多个 key 之间怎么选？不只看"现在谁余量多"，还要看"最近谁靠谱"——两个信号相乘。

### 展开讲（30秒版本）
- 每个 key 维护 **60 秒滑动窗口**：TPM、RPM、当前并发
- 选 key 得分 = min(三个归一化余量) × (1-0.4+0.4×成功率) × 0.7^限流连击数
- 效果：刚被限流的 key 自动沉底，恢复后自动回来；全程无人工干预

### 为什么这么设计（面试官问"为什么不轮询？"）
- 纯轮询会把请求均匀砸向正在退化的 key
- 瞬时余量决定"现在谁有空"，历史成功率决定"最近谁靠谱"，缺一不可
- 成功率样本不足时按中性处理（不奖不罚），避免冷启动偏差

### Java 对应物
Spring Cloud LoadBalancer 自定义 IRule／Ribbon 的权重策略；思想同 Nacos 权重路由。

### 可能的追问 & 答法
| 追问 | 答法 |
|------|------|
| 滑动窗口怎么实现的？ | `deque[(timestamp, count)]`，读取时 prune 过期项，O(窗口元素数)；TPM/RPM/并发各自一份 |
| 成功率权重为什么是 0.4？ | 经验值：太低起不到降权作用，太高会让偶发失败的 key 长期坐冷板凳；可配置化是后续方向 |
| 并发计数怎么保证原子性？ | 单 asyncio 事件循环内无抢占；若上线程需把 acquire/release 改为锁内操作 |

## 亮点二：熔断与半开探测

### 一句话
key 连续失败就"跳闸"冷却，但冷却结束不能直接满血复活——先放一个探测请求试试水，成功才合闸。

### 展开讲
三态转换：**closed（正常）→ open（冷却）→ half-open（半开探测）→ closed**
- 429 只短冷却 15 秒起步，连续限流按指数升级 15→30→60（封顶配置值），尊重上游 `Retry-After` 头
- 冷却到期不自动恢复：调度路径显式推进到半开，只放行**一个探测请求**
- 探测成功 → 完全闭合；失败 → 重新冷却且时长翻倍

### 关键设计决策（必考）
**为什么 429 不能当普通失败重罚？**
> 商汤的限流多是账号/平台级的，不是单个 key 坏了。我最初把 429 罚 60 秒冷却，结果两个 key 同时被限流时全部锁死，之后所有请求都 429——恶性循环。教训：**限流 = 让位，不等于惩罚**；真正的长冷却留给 401（key 失效）这类确定性故障。

### Java 对应物
Sentinel 的熔断降级 / Hystrix 断路器，同样是 closed-open-half-open 三态。你现在有手写版，比背八股强十倍。

### 可能的追问 & 答法
| 追问 | 答法 |
|------|------|
| 半开状态如果探测请求超时怎么办？ | 超时会走 record_failure 分支 → 触发重新冷却翻倍，不会卡死 |
| 怎么防止半开期涌入大量请求？ | 半开同时只允许一个在途探测令牌（probation_token），其余请求视 key 不可用 |
| 冷却时长封顶的意义？ | 防止指数升级后单 key 被罚到几分钟——平台限流窗口通常 ≤1 分钟，罚再久没意义 |

## 亮点三：SSE 流式桥接

### 一句话
AI 回答是一个字一个字蹦的，网关夹在中间当传声筒：上游太快要背压、客户端断开要取消、不管谁死都要体面收尾。

### 展开讲（三个子问题）
1. **背压**：有界队列（32 条），客户端消费慢时暂停读上游，内存不爆
2. **断连取消**：客户端关闭页面 → 取消 reader 协程 → 上游连接同步关闭，不留孤儿请求继续烧 token
3. **体面收尾**：reader 的每条退出路径（正常完成/异常/客户端取消）都必须让消费端能终止

### 最值钱的踩坑故事（面试讲这个）
> 我的测试套件曾经挂死 300 秒。排查发现：上游中途异常时，桥接层只塞了一条错误事件进队列，没发 `[DONE]` 结束标记——消费端永远阻塞在 `queue.get()`，生产环境表现就是**客户端拿着半个僵尸连接无限等**。修复：每条退出路径补发 `[DONE]`。修复后整个测试套从挂死变成 0.97 秒跑完。
>
> **教训**：异步生产者-消费者模式里，每一个 `return`、每一个 `except` 都要对齐"对面能不能知道你结束了"。

### 附带优化
流式请求自动注入 `stream_options: {"include_usage": true}`，上游拒收时自动剥离重试——让调度器拿到真实 token 数，否则 TPM 余量全是瞎猜。

### Java 对应物
Servlet `SseEmitter` 转发 / WebFlux `Flux<String>`；背压思想同 Reactor 的 request(n)。

### 可能的追问 & 答法
| 追问 | 答法 |
|------|------|
| 为什么队列设 32？ | 经验平衡点：太小背压太频繁影响吞吐，太大失去背压意义变纯缓冲 |
| 客户端断开你怎么知道的？ | StreamingResponse 的生成器被 cancel 时抛 CancelledError，finally 里清理并取消上游 task |

## 亮点四：动态模型发现（三级路由）

### 一句话
商汤上新模型我没改一行配置就能用了——网关定期问上游"你现在有哪些模型"，缓存 5 分钟。

### 展开讲
路由解析三级回退：
1. `route_to` 显式指定（最高优先级，人工裁决冲突）
2. 静态 `models` 配置
3. **动态目录**：实时拉上游 `/models`，TTL 缓存 5 分钟

动态拉取失败有 **60 秒负缓存**——不会每个请求都去打上游，失败也优雅回退到静态判定。实际战果：`sensenova-6.8-flash-lite` 上线当天，我的 `/v1/models` 里自动出现，直接调用成功。

### Java 对应物
Nacos/Eureka 服务发现 + 客户端缓存定期刷新；负缓存同 DNS 的 NXDOMAIN 缓存思路。

### 可能的追问 & 答法
| 追问 | 答法 |
|------|------|
| 缓存和配置不一致怎么办？ | TTL 到期自然刷新；管理端 reload 会主动失效缓存；静态声明优先于动态，保底可控 |
| 负缓存为什么需要？ | 上游挂了时避免每个请求都去探活形成重试风暴——60 秒内直接判定不可用 |

## ⭐ 亮点五：红蓝对抗评审（最加分的软实力故事）

### 一句话
功能上线前我派了两个互相独立的 AI 评审员，一个专攻安全、一个专攻逻辑正确性，从零读代码攻击自己的实现——抓出 2 个高危 bug。

### 故事完整版（90 秒，建议背下来）
> 我让两个没有上下文的评审代理分别以攻击者视角审代码。安全队确认了认证设计（常数时间比较、密钥脱敏）没问题，但指出 health 接口信息泄露和爆破无限速。逻辑队收获更大——抓出两个 HIGH：
>
> **第一个**：跨平台故障切换是我新上的功能，切换后我复用了旧平台的 provider 对象——等于拿着 A 平台的钥匙开 B 平台的门，切换后必然失败。单元测试全绿是因为 mock 场景里两个平台行为一致，真实场景类型不同才炸。
>
> **第二个**：流式重试换 key 时，旧 key 的并发额度没有释放。每次失败尝试泄漏一格并发，累积下去健康的 key 会被自己的并发上限饿死。
>
> **最大的感悟**：42 个测试全绿 ≠ 没 bug。测试覆盖的是"想到的路径"，评审员找的是"没想到的路径"。修复后我把这两个案例写成了回归测试，现在 46 个用例。

### 这段话展示的能力（面试官真正在听的）
- 对自己代码的怀疑精神（不护短）
- 理解"测试通过"和"正确"的区别
- 把事故转成回归测试的闭环习惯
